PaySoft v2 — Master Plan

Sequencing authority for the build: 11 phases, 12 long-lived branches, one deployable system at every step.

Overview

This is the sequencing authority for the PaySoft v2 build. It takes the 13 production layers defined in BUILD_PROCESS_13_LAYERS.html (the what and why) and orders them into buildable phases (the when and how), with one long-lived git branch per layer.

1. Constraints & Rules of Engagement

Only two platforms are used for the entire project: GitHub and Cloudflare. Where the blueprint referenced third parties, these substitutions apply:

Blueprint mentionWhat we use insteadWhen
Resend / SendGrid / SES (Engine 7 email)Cloudflare Email Service — send_email Worker bindingPhase 3
WhatsApp / SMS alerts (Engine 7)Deferred. Engine 7 built behind a Notifier interfacePost-launch
UptimeRobot (Layer 13 monitoring)Cloudflare Health ChecksPhase 10
External Logpush SIEM (Layer 12)Workers Logs + D1 audit_logs table onlyPhase 9

Permanent Workflow Rules

  1. main is always deployable. Nothing merges without green CI.
  2. layer/* branches are long-lived and never deleted.
  3. feat/* and fix/* branches are short-lived: branch from a layer branch, merge back, delete.
  4. One phase at a time. A phase ends only when its Definition of Done is met and its branch is merged into main.
  5. Every phase ends with a working deployment — you always have a live, usable system.

2. Prerequisites

  • Node.js v22+, pnpm, gh CLI (authenticated), wrangler (authenticated)
  • Cloudflare account on the Workers Paid plan ($5/mo — required for Durable Objects in Phase 3 and Queues in Phase 5)
  • Domain decision: a custom domain unlocks Cloudflare Access (Phase 2), Email Sending (Phase 3), WAF rules (Phase 7), and Health Checks (Phase 10)

Branch Rules

  • During the initial build (Phases 0–11): each new layer branch is cut from main after the previous phase merges.
  • After the build (EVOLVE stage): merge main into that layer's branch to sync it, do the work, then PR the layer branch back into main.
  • Never delete a layer/* branch. Always delete merged feat/* / fix/* branches.

5. Build Order Rationale

Layers are not built in numeric order — they are built in dependency order, so every phase has a working system to stand on:

  1. Setup first (Layers 5+7): repo, deployment pipeline, D1.
  2. Data before logic (Layer 3): engines and auth need tables and repositories.
  3. Auth before engines (Layer 4): every engine endpoint is org-scoped from birth.
  4. Engines before UI (Layer 2): the frontend is built against real, deployed APIs.
  5. UI makes it a product (Layer 1): end of Phase 4 = a usable payroll app.
  6. Compute makes it scale (Layer 6): queues for bulk work, AI chatbot.
  7. Then production hardening, in an order where each phase uses the previous.

Phase 0 Setup & Foundations

Branch: layer/00-setup · Owns: Layers 5+7 · Depends on: nothing

Goal: A GitHub repo grown from the genome skeleton, with a hello-world Worker live on Cloudflare and a CI/CD pipeline that deploys main automatically.

Tasks

  1. Grow the organism in place — copy skeleton/ contents to project root; fill placeholders.
  2. Create the D1 database: wrangler d1 create paysoft → paste database_id into wrangler.jsonc.
  3. Hello world: Hono app with GET /api/health returning { ok: true, version }.
  4. Tooling: add scripts — dev, build, deploy, test, lint, typecheck.
  5. CI/CD — .github/workflows/deploy.yml: lint → typecheck → test → deploy preview (PR) → deploy production (main).
  6. GitHub repo: gh repo create paysoft --private --source=. --push.
  7. Branch protection on main: require PR, require test pass.
  8. Project management: GitHub Projects board, issue templates.
  9. Cut the 12 layer branches from main now.
  10. Update AGENTS.md placeholders for this organism.

Definition of Done

  • git push to main → CI green → https://paysoft.<subdomain>.workers.dev/api/health returns OK
  • A test PR gets a preview deployment and cannot merge with failing checks
  • wrangler d1 execute --remote can query the (empty) database
  • All 12 layer/* branches exist on GitHub; main is protected

Phase 1 Database & Storage

Branch: layer/03-database · Owns: Layer 3 · Depends on: Phase 0

Goal: The persistence layer is real: all tables migrated, seeded, and every read/write passes through org-scoped repositories.

Tasks

  1. Define Drizzle schema — 8 tables, every one carrying org_id.
  2. drizzle-kit generate → SQL → apply local and remote.
  3. Create R2 bucket paysoft-uploads; document key layout.
  4. Build repository layer — orgId required on every function.
  5. Write seed.py — 385 employees across 19 departments.
  6. Vitest integration tests against local D1.

Definition of Done

  • Migrations applied; SELECT COUNT(*) FROM employees = 385
  • R2 bucket exists and accepts a test object
  • Repository test suite green, including cross-org read returning nothing

Phase 2 Auth & Permissions

Branch: layer/04-auth · Owns: Layer 4 + Engine 1 · Depends on: Phase 1

Goal: Nobody touches anything without a session; nobody sees anything outside their org; roles gate every sensitive action.

Tasks

  1. Migration for users and sessions tables (Lucia schema).
  2. Lucia setup — httpOnly, secure, SameSite cookies.
  3. Engine 1 endpoints: login, logout, me, refresh.
  4. Middleware chain: session validation → org_id + role injection → requireRole(...).
  5. Seed users for the demo org, one per role.
  6. Zod validation on all auth payloads.
  7. If custom domain: configure Cloudflare Access.
  8. Tests: login flow, role gating, cross-org isolation.

Definition of Done

  • Login → session cookie → GET /auth/me returns user with role + org
  • RBAC matrix enforced; employee role can only reach its own record
  • Cross-org isolation test passes against the deployed Worker

Phase 3 Backend Engines

Branch: layer/02-backend · Owns: Layer 2 (Engines 2–7) · Depends on: Phase 2

Goal: The whole brain of PaySoft, deployed as a typed API. Build as feat/* branches off layer/02-backend.

Engine Build Order

  1. feat/engine-3-tax — pure functions, FY 2025-26 slabs, HRA, 80C/80D/24b, EPF, ESI, PTax.
  2. feat/engine-4-payroll — PayrollRunLock DO, LOP/arrears/bonus math, lifecycle Draft → Frozen.
  3. feat/engine-2-audit — org scan for missing data, severity levels.
  4. feat/engine-5-ess — Form 12BB, leave, regime simulator.
  5. feat/engine-6-docs — PDF payslips, Form 16, ECR, ESI returns, bank advice.
  6. feat/engine-7-notify — Notifier interface with Cloudflare Email Service.
  7. Export Hono RPC types for the frontend.
  8. Basic audit_logs writes on payroll runs.

Definition of Done

  • Full API surface deployed and org-scoped; RPC types exported
  • E2E test: seed org → run payroll → frozen → payslip PDF → second run rejected by DO lock
  • Engine 3 unit-test suite covers every slab, cap, rebate, and regime comparison

Phase 4 Frontend

Branch: layer/01-frontend · Owns: Layer 1 · Depends on: Phase 3

Goal: PaySoft becomes a product — every screen rebuilt as a fast Astro PWA. Milestone: usable application.

Tasks

  1. Initialize Astro inside app/pwa/ (static output, Tailwind, React islands).
  2. Shared layout with sidebar; routes: /login, /dashboard, /employees, /employees/:id, /salary-stats, /annual-statements, /reports, /ess, /admin.
  3. Screens per blueprint, each island calling the real API via RPC types.
  4. Chatbot UI shell on /ess.
  5. Design fidelity: match the v1 screenshots.
  6. Login page form calling Engine 1.

Definition of Done

  • Log in → dashboard with audit checklist → run payroll → download payslip PDF
  • All v1 screens exist and visually match references
  • Pages ship minimal JS (islands only); tables sort/filter/paginate client-side

Phase 5 Cloud & Compute

Branch: layer/06-compute · Owns: Layer 6 · Depends on: Phase 4

Goal: Heavy async fan-out (Queues) and AI (Workers AI + Vectorize).

Tasks

  1. Queues: create queue, binding + consumer. Producers: Engine 6 bulk, Engine 7 dispatch.
  2. PayrollRunLock progress: extend DO to persist run progress for crash recovery.
  3. Chatbot: Vectorize index seeded with tax rules/FAQs; query → Workers AI → stream.
  4. Queue failure handling: retries + dead-letter queue.

Definition of Done

  • Bulk payslip generation for 385-employee seed org completes via queue
  • Chatbot answers tax questions with retrieved context, streaming in the UI
  • Payroll run status reflects DO-persisted progress

Phase 6 Caching & CDN

Branch: layer/10-caching · Owns: Layer 10 · Depends on: Phase 5

Goal: Stop re-computing what rarely changes. Introduces KV patterns Phase 8's rate limiter reuses.

Tasks

  1. Create KV namespace + binding; build getCached(key, ttl, fetchFn).
  2. Cache per blueprint: tax slabs (24h), PTax rules (7d), PF/ESI config (7d), sessions, audit results (5m).
  3. Cache-Control headers: static assets max-age=31536000, immutable; user-specific private, max-age=60.
  4. Invalidation: write-through on tax slab update; purge audit cache on payroll freeze.

Definition of Done

  • Repeat dashboard load performs measurably fewer D1 reads
  • Tax slab change visible immediately after write-through
  • No user-specific data served from a shared cache tier

Phase 7 Security & RLS

Branch: layer/08-security · Owns: Layer 8 · Depends on: Phase 6

Goal: Defense in depth, verified layer by layer — the hardening pass.

Tasks

  1. Turnstile on the login form; server-side verification middleware.
  2. Zod validation sweep: every endpoint's input validated.
  3. Security headers: CSP, HSTS, X-Frame-Options, nosniff.
  4. WAF managed rules on the domain.
  5. The RLS audit: read every repository function; prove org_id filtering.
  6. Verify payslip PDFs are DOB-password-protected.

Definition of Done

  • Login rejects bots without a Turnstile token
  • Every endpoint rejects malformed input with a clean 400
  • RLS audit checklist with a passing test per repository function

Phase 8 Rate-Limiting

Branch: layer/09-rate-limiting · Owns: Layer 9 · Depends on: Phase 7

Goal: Nobody can overwhelm the system — at all three levels (API, business logic, bot).

Tasks

  1. KV-backed rate-limiter middleware (reuses Phase 6 KV patterns).
  2. Per-route limits: login 5/min/IP, API 100/min/user, payroll run 1/min/org.
  3. Confirm PayrollRunLock DO still serializes runs independently.
  4. Load test with k6: prove limits trip at the right thresholds.

Definition of Done

  • 6th login attempt in a minute returns 429 with Retry-After
  • Concurrent payroll-run requests for same org/month: exactly one proceeds
  • k6 report committed showing limits holding under 10x normal load

Phase 9 Error Tracking & Logs

Branch: layer/12-logging · Owns: Layer 12 · Depends on: Phase 8

Goal: You can see what the system is doing — and catch problems before users report them.

Tasks

  1. Structured JSON logging utility adopted in every engine.
  2. Error-boundary middleware: unhandled exceptions → 500 with trace ID.
  3. Complete audit_logs coverage: payroll runs, declaration approvals, employee creation.
  4. Admin audit-log viewer screen.
  5. Document the wrangler tail debugging workflow.

Definition of Done

  • One payroll run produces a readable, trace-ID-linked log trail
  • A forced error returns a 500 with trace ID findable in logs within seconds
  • "Show all payroll runs for the demo org" answerable from audit_logs

Phase 10 Availability & Recovery

Branch: layer/13-availability · Owns: Layer 13 · Depends on: Phase 9

Goal: Prove — by drilling it — that failure is boring: rollback in minutes, data recoverable, history immutable.

Tasks

  1. Rollback drill: deploy broken version → git revert → verify fix → time it.
  2. PITR drill: delete seed record → restore via D1 point-in-time recovery → verify.
  3. Freeze immutability test-suite extension.
  4. Cloudflare Health Checks on /api/health.
  5. Write docs/runbook.md.
  6. Scheduled R2 export of D1 snapshots.

Definition of Done

  • Rollback drill completed in under 10 minutes, end to end
  • PITR drill completed and documented in the runbook
  • Frozen-month tampering attempts all fail in tests

Phase 11 Load Balancing & Scaling

Branch: layer/11-scaling · Owns: Layer 11 · Depends on: Phase 10

Goal: Confidence that 1 org with 10 employees and 500 orgs with 100k employees run on the same architecture.

Tasks

  1. k6 load suite: concurrent orgs running payroll, salary-day payslip download spike.
  2. Measure: Worker CPU time, D1 write latency, queue drain rates.
  3. Tune queue consumer concurrency and batch sizes.
  4. Dashboard alerts: Workers CPU, D1 latency, queue depth, error rate.
  5. Write docs/scaling.md: current limits, org_id sharding strategy, trigger metrics.

Definition of Done

  • Load report committed: system handles 500 orgs / 100k employees (or documents where it doesn't)
  • Alerts fire in a forced-overload test
  • docs/scaling.md reviewed — sharding plan explainable

After the Build: Living in the Layered Repo

Once Phase 11 merges, the project enters the genome's EVOLVE stage. The 13 branches remain your permanent map:

  1. To change something, name its layer first. "Payslips need a new field" → Layer 3 (migration) + Layer 2 (Engine 6).
  2. Sync before work: git checkout layer/0X-name && git merge main.
  3. Work small: feat/* off the layer branch for anything bigger than a few lines.
  4. Merge back: PR layer branch → main → CI green → deploy.
  5. The layers compound: each project you build with this model makes the next one's phases faster to plan.
The 13 layers are the mental model; the branches are its memory; main is always the truth.
